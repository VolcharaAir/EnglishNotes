# Desktop + Supabase, протокол 2

Изменения подготовлены для ручного развёртывания. Приложение не запускает SQL,
не меняет тариф и не публикует себя. До настройки сервера доступна локальная работа.
Публичные настройки поставляются внутри EXE; преподавателю не нужны Python, .env,
аккаунт разработчика или Dashboard.

## Один раз — владельцу Supabase-проекта

1. Закройте старые версии приложения и сделайте резервную копию базы Supabase.
   Для локальной SQLite закройте приложение и скопируйте папку данных целиком.
   Сначала рекомендуется отдельная тестовая ветка/проект Supabase.
2. Убедитесь, что применена `20261117000100_lesson_sessions.sql`. Не запускайте её повторно.
3. В **SQL Editor**, от роли postgres, вручную выполните целиком
   `supabase/migrations/20261117000200_desktop_sync.sql`, включая BEGIN/COMMIT.
   Новая миграция сохраняет существующие серверные строки. Она закрывает старые
   прямые API-запросы и v1 RPC: старые тесты v1 после этого не являются проверкой v2.
   Таблица заметок исключается из Postgres Changes; используется private Broadcast.
4. В **Authentication → Hooks → Before User Created** выберите PostgreSQL-функцию
   **public.en_before_user_created** и включите hook. Доступ предоставлен только
   `supabase_auth_admin`; назначать функцию клиенту нельзя. Если hook недоступен
   в вашем интерфейсе/плане, облако пока не включайте.
5. Проверьте **Authentication → Sign In / Providers → Anonymous Sign-Ins**.
   В **Authentication → Rate Limits** задайте приемлемые ограничения регистрации
   и обновления токенов; не отключайте встроенную защиту Auth.
   Текущий Desktop использует автоматический anonymous sign-in без CAPTCHA.
   Если CAPTCHA уже обязательна, signup будет отклонён: не отключайте защиту
   вслепую, сначала согласуйте её с этой моделью и протестируйте в отдельной ветке.
6. В настройках **Realtime** отключите публичные каналы (Allow public access),
   установите доступные ограничения подключений/событий в пределах Free.
   Проект предполагается выделенным для EnglishNotes: restrictive-политики
   `realtime.messages` намеренно запрещают другие клиентские каналы и отправку
   Broadcast клиентом. Для проекта с другими приложениями нужна отдельная проверка.
7. В **Data API → Exposed schemas** оставьте public; не добавляйте
   `englishnotes_private`. Не выдавайте клиенту доступ к служебным таблицам.
8. Только после включения hook разрешите облачные операции в SQL Editor:

   ```sql
   UPDATE englishnotes_private.cloud_limits
   SET auth_hook_ready=true, enabled=true WHERE id;
   ```

   `auth_hook_ready` — подтверждение настройки оператором, не автоматическое
   обнаружение конфигурации GoTrue. Не устанавливайте его до шага 4.
9. Выполните read-only `supabase/verify_desktop.sql`. Проверьте permissions,
   RLS и лимиты; отсутствие `lesson_notes` в publication теперь ожидаемо.
10. Подготовьте EXE с публичной конфигурацией и выполните живые проверки ниже.
    Не распространяйте сборку, пока не проверены hook и private Realtime.

Официальные описания:
[Auth hook](https://supabase.com/docs/guides/auth/auth-hooks/before-user-created-hook),
[Realtime authorization](https://supabase.com/docs/guides/realtime/authorization),
[Broadcast](https://supabase.com/docs/guides/realtime/broadcast).

## Сборка для распространения

На Windows с установленным окружением разработки:

```powershell
uv sync --locked --extra dev --extra build
uv run --no-sync pytest -q
uv run --env-file .env --no-sync python tools/prepare_cloud_config.py
uv run --no-sync python -m PyInstaller --clean --noconfirm EnglishNotes.spec
```

Результат: `dist\EnglishNotes.exe`. В bundle попадают только HTTPS origin и
`sb_publishable_...`; tool отвергает secret/legacy JWT ключи. .env, SQLite и
токены пользователей не включаются. Для намеренно локальной сборки выполните
`python tools/prepare_cloud_config.py --local` перед PyInstaller.
Пересоздавайте конфигурацию перед каждой сборкой: spec требует подготовленный файл.

В GitHub **Settings → Secrets and variables → Actions → Variables** задайте
`SUPABASE_URL` (без `/rest/v1/`) и `SUPABASE_PUBLISHABLE_KEY`.
Это публичные настройки, не service_role/secret. SQL security job использует одноразовый PostgreSQL и не получает ключей.
Windows build зависит от его успеха. Workflow подготовлен, но в этом
этапе не запускался и не публиковал сборку. Не создавайте тег, пока не нужен релиз:
существующий release-job публикует релиз только при push тега `v*` после тестов.

Разработка с .env: `uv run --env-file .env python -m englishnotes`.
Обычные пользователи запускают настроенный EXE двойным щелчком без переменных окружения.

## Как это работает

- Любой экземпляр нового профиля получает собственный Supabase UID; нет списка
  разрешённых аккаунтов и привязки к владельцу программы.
- Refresh token хранится в Windows Credential Manager / macOS Keychain /
  Linux Secret Service. Access token существует только в памяти. Небезопасного
  файлового fallback нет. При недоступном хранилище продолжается локальная работа.
- При недействительном refresh token приложение не создаёт замену аккаунту молча.
  Анонимный аккаунт нельзя восстановить на другом компьютере одной копией SQLite.
  Не удаляйте запись Credential Manager, если хотите сохранить доступ к облаку.
  Экспорт/перенос анонимной личности между ПК в этот этап не входит.
- «+ Новое занятие» остаётся локальным. «Создать занятие» создаёт общее занятие,
  «Пригласить участника» позволяет явно опубликовать существующее локальное.
  Частные занятия не отправляются автоматически.
- Код: 256 случайных бит, в серверной таблице только SHA-256, однократный,
  по умолчанию действует 30 минут. Клиент хранит полученный код в системном vault.
  При потерянном ответе create сервер может перевыпустить неиспользованный код,
  не продлевая срок; уже использованный код не восстанавливается.
- Создатель имеет право завершить занятие. Оба участника редактируют заметки.
  Названия ролей student/teacher сохранены из v1: создатель/student, второй/teacher;
  это не закрепляет возможности за конкретными людьми.
- SQLite v2 добавляет `cloud_*` таблицы/триггеры, не меняя значения прежних
  lessons/notes. Локальная запись и outbox фиксируются одной транзакцией.
- Worker имеет собственное SQLite-соединение. Он отправляет ограниченные пачки,
  сохраняет неизменный in-flight запрос для повтора, а ответы складывает в inbox.
  GUI сначала сохраняет буфер редактора, затем применяет inbox без эха в outbox.
- Private Broadcast передаёт только сигнал `changed`, без текста заметки.
  Данные читаются через ограниченный RPC с последовательным курсором, по событию
  и каждые 20 секунд как страховка. Страница ограничена 64 записями и целевыми
  4 MiB; одна большая заметка прежнего v1 формата читается отдельно. Клиент
  ограничивает ответ 16 MiB, включая JSON escaping и метаданные. Отключение WebSocket не останавливает обмен.
- Версия серверной заметки сравнивается атомарно. При конфликте автоматической
  перезаписи нет: кнопка сравнения предлагает оставить свою/принять вторую версию.
  Исходные версии остаются в локальном `cloud_conflict_archive`, включая последнюю
  локальную правку. Удалённые локально заметки с конфликтами тоже доступны сравнению.
- После обрыва сети очередь сохраняется и повторяется с задержкой до 120 секунд.
  Ошибки лимитов/сервера не откатывают локальные записи. Завершённое занятие
  становится read-only; неуспевшие отправиться правки остаются локально в очереди.
- Подтверждения операций хранятся 7 дней. Очень старый повтор проверяется по версии
  и может потребовать ручного разрешения конфликта, но не перезаписывает новую версию.

## Серверные лимиты и аварийная остановка

Только администратор SQL изменяет singleton `englishnotes_private.cloud_limits`.
Изначально enabled=false. Значения одинаковы для всех пользователей:

| Параметр | По умолчанию |
|---|---:|
| requests_user_minute / writes_user_minute | 120 / 20 |
| requests_day / writes_day | 30000 / 2000 |
| sessions_user_day / sessions_day | 10 / 200 |
| sessions_user_active / sessions_user_total | 3 / 100 |
| sessions_total / accounts_total | 1000 / 1000 |
| signup_ip_hour / signup_day | 30 / 100 |
| invitation_minutes | 30 |
| note_bytes / notes_session | 16384 / 250 |
| stored_bytes / egress_day_bytes | 16 MiB / 64 MiB |
| safety_percent | 80 |

`sessions_user_active` ограничивает все активные членства, включая созданные
и присоединённые занятия. Private channels открываются только для активных занятий.

`note_bytes` — сумма UTF-8 байт заголовка и текста; tombstones тоже занимают
место/слот заметки. Приглашения дополнительно ограничены v1 лимитером 5 попыток
подключения в минуту на пользователя. Auth hook считает доверенный IP от GoTrue,
для IPv6 объединяет /64; IP хранится в счётчике только как хеш с приватной солью.
Глобальный предел аккаунтов ограничивает обход через множество адресов.
Старые минутные/суточные счётчики удаляются при периодическом обслуживании gate.

При 80% суточных запросов/записей/расчётного исходящего объёма открывается
предохранитель до следующего дня UTC. Storage ограничивает новые записи;
чтение локальной копии остаётся доступным. Суточные и IP счётчики регистрации
обслуживаются Auth hook; общий предел зарегистрированных аккаунтов постоянный.

Экстренная остановка:

```sql
UPDATE englishnotes_private.cloud_limits SET emergency_stop=true WHERE id;
```

После анализа причины оператор может снять `emergency_stop`/`limited_until`.
Не сбрасывайте счётчики автоматически ради продолжения записи сверх бюджета.

**Это ограничения операций приложения, не гарантия нулевого счёта или точного
порога долларов.** SQL оценивает логические данные, receipts и JSON-ответы с запасом,
но не весь размер PostgreSQL, WAL, индексов, Auth, TLS/Realtime, запросы, отклонённые
шлюзом, или DDoS. Нужны контроль Usage в Dashboard, лимиты Auth/Realtime и отдельный
Free-проект без платного upgrade/кредитных пополнений. При росте нагрузки — внешний
API/IP rate limiter. Приложение не имеет billing API/админ-ключа, не меняет тариф
и не совершает автоматических покупок. Защита не обещает доступность под атакой:
злоумышленник может исчерпать публичную квоту, после чего облако закрывается.

Windows smoke в CI устанавливает `ENGLISHNOTES_DISABLE_CLOUD=1`: он проверяет
запуск и локальную базу без создания тестовых аккаунтов на боевом сервере.
Живой интеграционный тест запускается отдельно и явно.

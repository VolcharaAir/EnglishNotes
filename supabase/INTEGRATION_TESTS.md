# Живой интеграционный тест безопасности Supabase

## Что готово, а что ещё не запускалось

Скрипт `tests/live_security.py` использует настоящий Auth REST API и PostgREST.
Он делает три отдельных anonymous sign-in, проверяет полученные JWT через
`GET /auth/v1/user`, затем выполняет 14 запрошенных сценариев и дополнительные
проверки сохранности данных/совместного редактирования. JWT используются ровно
в том виде, в котором их вернул Auth; ручного создания/подмены claims нет.

Первый запуск на ПК оператора дошёл до сверки фактически применённой схемы
и получил PASS. Первый Auth-запрос остановился с сетевой/TLS-ошибкой без
HTTP-ответа: общий статус **BLOCKED**. Успешные anonymous sign-in/JWT и проверки
изоляции ещё не подтверждены; уязвимости реального проекта пока не оценены.
Локально прошли **106 pytest-тестов**, включая 42 offline-теста runner-а и
диагностики. Они не подменяют живой результат. Read-only запрос экспорта
проверен на PostgreSQL 16; присланный экспорт Supabase PostgreSQL 17.12 также
прошёл сверку с миграцией.

Существующая SQL-миграция, политики, SQLite и код Desktop не изменены.
Никаких миграций/новых RPC для теста не требуется. Запуск намеренно отдельный:
приложение и обычный pytest/Windows workflow не запускают живой тест.

## Самый простой запуск на Windows

Потребуется Python **3.14+**. Сторонние Python-пакеты и Supabase SDK не нужны.
Готовый Desktop EXE не является интерпретатором внешних Python-скриптов.
Если Python отсутствует, сначала установите его с официального python.org;
RLS и настройки Supabase ради этого менять не нужно.

1. Обновите исходники проекта из GitHub. `.env` должен остаться **в корне проекта**,
   рядом с `pyproject.toml`. Не удаляйте старый `.env` и не публикуйте его в GitHub.
   Создайте в этом же корне папку `work`, если её ещё нет.
2. В Supabase Dashboard выберите **тот же проект**, что указан в вашем `.env`.
   Откройте SQL Editor → новый запрос. Вставьте **только**
   `supabase/tests/inspect_applied.sql` и нажмите Run.
   Это SELECT метаданных: он не читает записи пользователей и не меняет базу.
3. Сохраните полученный результат в JSON как
   `work/supabase-applied-schema.json`. Поддерживаются:
   сам JSON-объект, JSON-массив с одной строкой `schema_snapshot` и JSON-строка
   с вложенным объектом. Можно скопировать полное значение колонки в файл.
   Если Dashboard предлагает только CSV, экспортируйте в
   `work/supabase-applied-schema.csv`: этот формат также поддерживается.
4. Убедитесь, что ваш `.env` содержит только нужные вам настройки;
   тест использует `SUPABASE_URL` и `SUPABASE_PUBLISHABLE_KEY`.
   Нужен современный ключ `sb_publishable_...`, **не** secret/service_role.
   Не присылайте ключи или токены в чат.
5. Дважды нажмите `supabase/tests/run_live_security.cmd`.
   Он использует `.venv`, если она есть, иначе Python Launcher `py -3.14`.
   Обёртка читает разрешённые поля `.env` в окружение, не исполняя его содержимое
   и не печатая значения. Основной тест получает конфигурацию **только из env**.
6. Дождитесь результата. Отчёт: `work/supabase-live-report.json`.
   Проверьте поле `finished_at`, чтобы не принять отчёт старого запуска за новый.

Существующие переменные окружения имеют приоритет над `.env`. Если в оболочке
остались параметры другого проекта, очистите/исправьте их перед запуском.
Обёртка загружает только URL, publishable key, путь экспорта и CAPTCHA-токены;
service_role/secret key из `.env` она не загружает и не использует.

## Запуск разработчиком непосредственно из окружения

Обязательные переменные:

| Имя | Назначение |
|---|---|
| `SUPABASE_URL` | HTTPS-origin проекта без логина, query string и дополнительных путей |
| `SUPABASE_PUBLISHABLE_KEY` | Современный publishable key, не административный |
| `SUPABASE_SCHEMA_FILE` | Путь к экспорту `inspect_applied.sql` из этого проекта |

```text
python supabase/tests/live_security.py --report work/supabase-live-report.json
```

Основной скрипт сам `.env` не открывает. Локальная обёртка — альтернативный явный
способ заполнить окружение из существующего файла. Все запросы используют TLS
с обычной проверкой сертификата. HTTP-redirect не выполняется, чтобы случайно
не передать apikey/JWT другому адресу. URL, заголовки, полные ответы сервера,
refresh/access tokens, CAPTCHA и приглашение в лог/отчёт не копируются.

## Проверка фактически применённых определений

Сначала оператор экспортирует определения именно из своего проекта.
`inspect_applied.sql` возвращает тела и сигнатуры шести существующих функций,
включая обе public RPC и private helper-ы, реальные колонки/типы, ограничения,
политики и ACL. Пользовательские занятия/заметки/приглашения не экспортируются.

До первого Auth-запроса runner сверяет тела функций с существующей миграцией,
пустой search_path, реальные имена/типы входных RPC-аргументов и наборы колонок.
Различия останавливают запуск: исправления политик или переустановка миграции
не выполняются. Экспорт должен быть свежим и из того же проекта: файл не имеет
криптографической подписи и сам по себе не удостоверяет его происхождение.

Контракт текущей миграции: create принимает p_title, p_creator_role,
p_invitation_ttl; join — p_invitation_code. Табличные ответы RPC проверяются
как массив из одной строки; HTTP 200 без `outcome=ok` не считается успехом.
`lesson_sessions` выбирается явными колонками, без закрытого invitation_code_hash.

## Что выполняет тест

| Сценарий | Что должно произойти |
|---|---|
| 1–3 | A, B, C получают три разных UUID и Auth-issued JWT; каждый JWT подтверждён Auth API |
| 4 | A создаёт отдельное занятие с меткой security-test-…, created_by=A |
| Подготовка | A создаёт настоящую заметку до проверок C, чтобы пустой результат не был бессодержательным |
| 5 | B входит по коду, возвращается тот же lesson_id |
| 6 | Неверный код C: HTTP 200, invalid_invitation, lesson_id=null |
| 7–8 | C читает занятие/заметки: HTTP 200 и пустой массив |
| 9 | INSERT C: HTTP 403 + 42501; A отдельно подтверждает отсутствие вставленной строки |
| 10 | PATCH/soft-delete C: HTTP 200 и 0 строк; DELETE: HTTP 403 + 42501; исходная заметка не изменилась |
| 11 | INSERT/UPDATE/DELETE состава участников C: HTTP 403 + 42501 |
| 12–13 | B вставляет заметку с author_id=B, A видит её содержимое |
| Дополнительно | A и B могут менять заметки друг друга, автор сохраняется, revision увеличивается |
| 14 | B не может заменить created_by, поменять роль/удалить A; создатель остаётся A, участников ровно два |
| Дополнительно | B не может прочитать хеш приглашения |

Роль teacher/student не является владением. В этой миграции создатель задаётся
полем created_by; клиенту вообще не разрешены прямые изменения lesson_sessions.

Для каждого POST/PATCH/DELETE используется только созданное тестом занятие и
точные UUID тестовых заметок/участников. Общих UPDATE/DELETE без фильтров нет.
Чужие настоящие занятия пользователя тест не перечисляет и не изменяет.

## Результаты и ошибки

- **PASS / exit 0**: пройдены все проверки и все 14 сценариев.
- **FAIL / exit 1**: получен ответ, не соответствующий проверяемому условию.
  Смотрите HTTP status и разрешённый код ошибки в JSON. `requires_security_review`
  означает необходимость разбора, а не автоматически доказанную уязвимость.
- **NOT_RUN / exit 2**: отсутствуют настройки/экспорт или схема отличается;
  пользователи не создавались. Невыполненные сценарии не объявляются прошедшими.
- **BLOCKED / exit 2**: сеть, Auth/CAPTCHA/rate limit или ошибка runner-а
  остановили исполнение. Оставшиеся сценарии имеют NOT_RUN/INCOMPLETE.

Ошибки FK/неверного поля HTTP 400 не засчитываются как RLS-защита. HTTP 401
также не принимается вместо ожидаемого разрешения/отказа для валидного JWT.
При отказе подготовительного успешного вызова зависимые проверки не выполняются.
Повторные запросы создания автоматически не отправляются: таймаут может означать,
что сервер уже создал данные, но ответ потерялся.

## Возможная дополнительная настройка Supabase

- Anonymous Sign-Ins должны быть включены, API/schema public доступны,
  существующая миграция — применена. Новые таблицы, RPC и grants не требуются.
- Если включена CAPTCHA, нужны **три свежих** токена для выбранного провайдера:
  `SUPABASE_CAPTCHA_TOKEN_A`, `_B`, `_C`. Получите их обычным поддерживаемым
  пользовательским потоком и задайте в env; не передавайте в чат. Тест не решает
  CAPTCHA автоматически и не отключает защиту рабочего проекта.
- Auth может ограничивать anonymous sign-up по IP/квоте. При 429 результат
  BLOCKED: дождитесь разрешённого окна или проверьте настройки тестового проекта.
  Отключать RLS или использовать service_role ради теста нельзя.
- Живой Realtime-транспорт в этом тесте не проверяется. Это отдельный сценарий;
  Desktop-синхронизация по-прежнему отсутствует.

## Тестовые данные после запуска

Остаются три анонимных аккаунта, одно занятие и тестовые заметки. При ранней ошибке
их может быть меньше. ID записаны в `fixtures` отчёта; это идентификаторы, не JWT.
Приглашение и токены в отчёте отсутствуют. Попытка локального sign-out выполняется
в finally; access token не записывается на диск. Logout не гарантирует мгновенный
отзыв уже выданного access JWT во всех сервисах до его истечения.

Автоматического административного удаления нет: обычному клиенту оно запрещено
и тест не обходит ограничения. После проверки в Dashboard можно вручную удалить
**только тестовое занятие по точному ID** (его заметки/членства каскадируются),
затем три тестовых Auth-пользователя по ID из отчёта. Сначала занятие: FK RESTRICT
иначе защищает автора/создателя от удаления. Не удаляйте общие таблицы/политики.
При потерянном ответе Auth ищите метку запуска в user_metadata новых тестовых
аккаунтов; не удаляйте неизвестные записи. Отчёты храните локально в игнорируемой
папке work и не добавляйте их вместе с `.env` в репозиторий.

## Если получен Network/TLS request failed

Запустите **run_connection_check.cmd** из той же папки tests после обновления
файлов supabase. Диагностика использует тот же .env, TLS-контекст и прокси,
но выполняет только один GET /auth/v1/settings: не создаёт пользователей,
не получает JWT и не пишет в БД. Исходный тестовый отчёт она не перезаписывает.

Разрешено прислать весь её короткий вывод. В нём нет URL, значений ключей,
прокси-адресов/паролей, сертификатов, токенов или свободного текста исключений.

| Код | Что проверять дальше |
|---|---|
| DNS_LOOKUP_FAILED | Правильность Project URL в .env и разрешение имени в вашей сети |
| TLS_CERT_VERIFY_FAILED | Системную дату/время, доверенные CA Python/Windows и HTTPS-перехват прокси/антивирусом |
| TLS_ERROR | TLS-соединение; не исправляйте отключением проверки сертификатов |
| CONNECTION_TIMEOUT / CONNECTION_REFUSED / CONNECTION_RESET | Доступность сети/прокси и разрешение соединения к API проекта |
| PROXY_TUNNEL_FAILED | Настройки и авторизацию используемого HTTPS-прокси |
| TRANSPORT_ERROR | Нужна дальнейшая диагностика без публикации полного исключения |
| HTTP_RESPONSE=200 | GET настроек Auth доступен; можно повторить основной тест один раз |
| HTTP_RESPONSE=401/403 | HTTP-ответ есть; проверьте соответствие URL и publishable key выбранному проекту |
| HTTP_RESPONSE=301/302 | Адрес перенаправляет; используйте прямой Project URL, ключи на redirect не пересылаются |

Флаги HTTPS_PROXY_CONFIGURED/CUSTOM_CA_CONFIGURED показывают только наличие
настройки, не её значение. Диагностика ничего не меняет в прокси/хранилище
сертификатов. Не используйте verify=False/отключение TLS и не меняйте RLS
для устранения транспортной ошибки. Не повторяйте signup многократно:
при потерянном ответе состояние сервера может быть неизвестно.

# Проверки Desktop v2

В Linux выполнены 152 pytest проверки, Ruff и SQL-контракты PostgreSQL 16.16.
Пользователь отдельно предоставил PASS живого Desktop v2: 19 проверок, журнал
Windows-сборки и подтверждение ручного обмена между двумя EXE, включая offline,
перезапуск и отправку очереди после восстановления связи.

Подробности и границы подтверждения: [Windows test report](windows-test-0.3.0.md),
[общий отчёт](implementation-report-0.3.md).

## Автоматические проверки

```text
uv run --no-sync pytest -q
uv run --no-sync ruff check src tests tools packaging
uv run --no-sync ruff format --check src tests tools packaging
python supabase/tests/check_sql.py --desktop
```

Последняя команда требует Docker и запускает только одноразовый PostgreSQL
без сети. Контейнер удаляется в finally. Параметр `--docker-host` необязательный.
Файлы bootstrap/security из supabase/tests **не запускайте в Dashboard**.

Покрытие клиентских тестов:

- два независимых клиента/профиля, создание/подключение, заметки, правки и удаления;
- сохранение автора при редактировании другим участником;
- offline outbox, закрытие/открытие SQLite, восстановление отправки;
- потеря HTTP-ответа и новая локальная правка до повторной отправки;
- одновременные изменения, сохранение обеих версий, ручное разрешение,
  отказ применять устаревший диалог, конфликт удаления;
- flush буфера GUI перед inbox, сохранение позиции курсора;
- приватные локальные занятия не отправляются, коллизия UUID не прикрепляет их;
- добавочная миграция SQLite v1→v2 сохраняет исходные строки;
- отказ vault не разрешает сетевые операции от неперсистированной личности;
- refresh сохраняет UID, ошибка не заменяет прежний анонимный аккаунт;
- выбран системный backend без файлового fallback;
- private Realtime protocol, проверка join ACK, invalidation;
- bundle содержит только публичные настройки и отвергает privileged key;
- прежние тесты локального приложения и диагностики также сохранены.

Это детерминированные тесты с transport/vault fixtures. Они не выдают тестовые
строки за настоящие JWT и не подтверждают фактическую работу GoTrue/WebSocket.

Проверки SQL исполняют обе миграции настоящим PostgreSQL и проверяют:

- RLS/ACL, запрет прямого API и v1 обходов, скрытие приглашений;
- создание/второй участник, однократный код и восстановление потерянного join-ответа;
- посторонний не читает/не пишет; второй участник не завершает занятие владельца;
- optimistic CAS, idempotency, ограничение размера, закрытое занятие read-only;
- NULL не снимает ограничение размера страницы;
- шесть крупных legacy-заметок (включая JSON escaping) читаются тремя
  ограниченными страницами без пропусков;
- policy private Broadcast допускает участника, отсекает постороннего;
- signup IP quota, обязательный доверенный IP и глобальный предел аккаунтов;
- пользовательский rate limit, размер и число заметок, истечение приглашения,
  storage quota, общий предел занятий, emergency stop,
  автоматический egress circuit breaker;
- пять гонок за второе место: ровно одно подключение;
- параллельный подбор: пять попыток, семь отказов, все 12 учтены;
- две параллельные записи одной серверной ревизии: один commit и один conflict.

SQL fixture задаёт PostgreSQL role/GUC в изолированной базе. Это проверка SQL,
**не** проверка настоящих JWT. Auth и Realtime в fixture заменены минимальными
схемами. Фактическое поведение Supabase проверяется отдельно.

## Живая проверка после ручной настройки Dashboard

После шагов из [cloud-desktop.md](cloud-desktop.md), в окружении разработки:

```powershell
uv run --no-sync python supabase/tests/live_desktop.py --run
```

Скрипт читает только разрешённые переменные из локального .env, не печатает значения,
использует public key и настоящие токены Auth, сохраняемые в системном vault.
Создаёт три независимых анонимных тестовых профиля и одно занятие, расходует квоты.
Повторные запуски используют те же личности через refresh. Тестовые базы остаются
в `work/desktop-live/A`, B, C для анализа; не удаляйте vault между запусками.

Проверяет настоящие private subscriptions A/B, явный отказ подписки C,
доставку события B→A, RPC, авторство,
conflict/resolve, reopen/offline queue, удаления, закрытие, отказ постороннему и
проверку права владельца. Не имитирует JWT вручную. Коды выхода:
0=PASS, 1=проверка провалилась, 2=BLOCKED/NOT RUN. Невыполненные проверки не PASS.
При завершении скрипт пытается закрыть созданное тестовое занятие, не удаляя
заметки и профили. Намеренное исчерпание глобальных квот на общем сервере не выполняется.
На Windows можно дважды нажать `supabase/tests/run_live_desktop.cmd` после установки
окружения разработки.

Если включена CAPTCHA, vault заблокирован, миграция не применена, hook не включён,
лимиты исчерпаны или private Broadcast не настроен, результат может быть BLOCKED.
Не снимайте защиту и не увеличивайте квоты вслепую ради зелёного результата.
Проверьте Auth Logs/Realtime Logs в Dashboard без публикации токенов.

## Ручная проверка двух компьютеров

1. Сохраните резервные копии старых локальных папок данных, закройте старый EXE.
2. Запустите настроенную новую сборку на двух компьютерах под разными Windows
   пользователями. Каждый должен автоматически получить собственную личность.
   На одном ПК для разработческой проверки можно задать разным процессам разные
   абсолютные `ENGLISHNOTES_DATA_DIR`, например `D:\EnglishNotesTest\A` и B.
   Это опция разработчика; обычному пользователю она не нужна.
3. На A создайте общее занятие, скопируйте приглашение, подключите B.
   Сравните названия/историю. Сохраните код только для этой проверки.
4. Создайте заметки с обеих сторон, измените их, удалите одну. Изменения второго
   участника должны появиться автоматически, автор должен сохраниться.
5. Отключите сеть на обоих ПК, отредактируйте одну общую заметку по-разному.
   Включите сначала A, затем B. На B должен появиться конфликт; сравните версии,
   сохраните выбранную и убедитесь, что оба видят итог. Проверьте удаление vs правку.
6. Отключите сеть, введите заметку, дождитесь локального сохранения, закройте EXE.
   Запустите снова без сети: запись должна остаться. Включите сеть, дождитесь
   уменьшения очереди, проверьте запись на другом ПК.
7. Закройте приложение, перенесите только EXE в другую папку и запустите:
   занятия и анонимная личность должны сохраниться в прежнем профиле.
8. На третьем независимом профиле неверный/использованный/истёкший код должен
   отклоняться. Включение Auth Hook и границы регистрации отдельно проверяйте
   в тестовой ветке Supabase, не блокируя действующих пользователей.
9. B не должен завершать занятие A. После завершения A оба читают историю,
   но не отправляют новые правки. Неотправленные локальные данные не удаляются.
10. В тестовой ветке уменьшите `note_bytes`, `writes_user_minute`, `sessions_user_active`,
    `signup_ip_hour`, `egress_day_bytes`, проверьте реальные отказы и local outbox.
    Включите emergency_stop, проверьте локальную работу; снимите остановку после
    анализа. Сохраните/восстановите прежние значения только в этой тестовой ветке.
11. В Usage проверьте реальное потребление; SQL-счётчики — защитная оценка,
    не точный прибор платёжного биллинга.

Windows EXE и живой Supabase проверялись пользователем на его компьютерах.
Их результаты зафиксированы в [отдельном отчёте](windows-test-0.3.0.md);
они не выдаются за запуск в облачной Linux-среде.

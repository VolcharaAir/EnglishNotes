# Архитектура текущего этапа

## Границы модулей

`app.py` — единственная точка сборки зависимостей: создаёт QApplication, определяет
путь базы, удерживает QLockFile, открывает Database, создаёт репозиторий, сервис и окно.
После выхода из цикла Qt закрывает соединение и освобождает блокировку.

`domain` содержит неизменяемые модели и ошибки, без зависимостей от Qt и SQLite.
`application` содержит сценарии и протокол `NotesRepository`.
`storage` реализует этот протокол. `ui` обращается только к сервису и моделям:
SQL-запросов и путей базы в интерфейсе нет. Сервис не зависит от конкретного хранилища.
`sync` выделен как будущий адаптер; сейчас это только пакет с описанием границы,
без фиктивной синхронизации, SDK, сетевых запросов или UI подключения по коду.

## Локальная модель и целостность

- `lessons` и `notes`: UUID, время создания/изменения в UTC, целочисленная ревизия,
  `deleted_at`. Отметка удаления заметки сохраняется для будущего обмена удалениями.
- `notes.lesson_id` — внешний ключ, проверки принадлежности выполняются при изменении
  и удалении. Скрытые/отсутствующие записи недоступны обычным сценариям.
- Параметризованные SQL-запросы сохраняют кавычки и пользовательский текст как данные.
- Изменения выполняются в `BEGIN IMMEDIATE` с commit/rollback. Миграции также атомарны;
  их номер хранится в `PRAGMA user_version`. Неизвестная более новая схема отклоняется
  без сброса или пересоздания пользовательской базы.
- Ревизия проверяется под блокировкой записи: устаревшая модель вызывает `ConflictError`.
  Это защита от тихой перезаписи, но ещё не механизм разрешения облачных конфликтов.
- Удаление — логическое. Физическая очистка и сроки хранения пока не реализованы.
- Времена обновления — метаданные интерфейса, не доверенный глобальный порядок событий.
- Занятия сортируются от новых к старым, заметки — по времени создания. Редактирование
  не меняет порядок и не вызывает скачки выделения.

Интерфейс хранит несохранённый текст в редакторе, а записанную ревизию — в модели.
Отложенное сохранение ограничено 2 секундами даже при непрерывном вводе. Перед уходом
с записи выполняется синхронный flush. При ошибке модель не объявляется сохранённой,
действие перехода отменяется. Сохранение названия занятия и заметки — отдельные атомарные
операции: если первая успешна, а вторая нет, повторяется только несохранённая часть.

SQLite-соединение используется в потоке GUI; для этого объёма операций это простая
предсказуемая основа. При внешней блокировке SQLite может ожидать до 5 секунд.
Будущему фоновому процессу синхронизации потребуется собственное соединение;
нельзя передавать существующее соединение между потоками.

## Будущая синхронизация — требования, без реализации

Потребуются отдельные модели участников/членства, облачные идентификаторы и версии схемы,
репозиторий учётных данных, журнал изменений/outbox, подтверждение обмена, повтор запросов,
идемпотентность, разрешение конфликтов и правила очистки tombstones. UUID и ревизии позволяют
добавить это миграциями, сохранив текущие локальные сценарии и контракт сервиса.
Текущая схема не заявляется готовым протоколом совместной работы.

Локальное сохранение должно оставаться независимым от сети. Обмен запускается отдельно,
ошибка сервера не отменяет запись в SQLite. UI и сервис не должны вызывать SDK Supabase.

Код занятия — приглашение, а не доказательство прав доступа. Сервер должен выдавать
короткоживущую сессию участника после безопасного обмена приглашением, ограничивать
попытки подбора, поддерживать истечение/отзыв приглашений. Каждая операция проверяет
членство и роль (владелец/редактор/читатель) на сервере. Нужны RLS-политики Supabase и
серверная проверка полномочий; ограничения только в интерфейсе недостаточны.
Учётные данные сохраняются через Windows Credential Manager/DPAPI; административный
доступ остаётся на сервере. Конкретный протокол авторизации проектируется отдельно.

## Будущий Windows EXE и GitHub Releases — требования, без реализации

Целевой путь преподавателя: открыть GitHub Releases → скачать `EnglishNotes.exe` →
двойной щелчок → ввести код занятия → начать работу. Установка Python, Git, VS Code,
ручная настройка SQLite, Supabase и консоль пользователю не нужны.

У приложения уже есть единая точка входа `englishnotes.app:main`, пакетная структура,
отсутствие зависимости от cwd и автоматическое создание базы в D:\EnglishNotesData.
Это позволяет позднее добавить PyInstaller entry point с оконным режимом и встроенным
Python/Qt. Временная папка распаковки EXE и каталог установки всегда остаются только
для ресурсов. Данные сохраняются по тому же пути при обновлении EXE.
По уточнённому требованию приложение не использует C: для собственных данных.
Будущая упаковка обязана размещать runtime на D: (или использовать onedir).

На следующем этапе упаковки потребуется PyInstaller-сборка на Windows runner,
проверка зависимостей/Qt-плагинов, запуск на чистой Windows без Python, подпись кода,
проверка репутации/SmartScreen и публикация проверенного EXE с контрольной суммой.
GitHub Actions должен собирать релизы по версионным тегам и публиковать артефакты
в GitHub Releases. Workflow, `.spec` и готового EXE сейчас нет.

Публичный URL Supabase и publishable key могут поставляться как встроенная конфигурация;
они не должны считаться секретами и давать административные права. Нельзя включать
service-role/secret key, пароль БД, ключи подписи или административные учётные данные.
Секреты сборки/подписи должны оставаться в GitHub Secrets с минимальными разрешениями.
Запуск приложения не должен требовать `.env` или ввода инфраструктурных параметров.

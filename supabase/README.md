# Первая серверная миграция EnglishNotes

Миграция подготовлена отдельно от работающего приложения. Она не запускается
из приложения, Windows workflow или тестов pytest. `.env` здесь не читается.
В реальный Supabase-проект миграция разработчиком не применялась.

## Применение через Supabase Dashboard

1. Откройте проект **EnglishNotes** и проверьте, что выбран нужный проект.
   Сначала рекомендуется отдельный тестовый проект/ветка. Если в проекте есть данные,
   сохраните резервную копию перед DDL-изменениями.
2. **Authentication → Providers / Sign In → Anonymous Sign-Ins**: проверьте,
   что анонимный вход включён. После такого входа пользователь получает UUID и JWT
   с ролью `authenticated`. Ключ publishable без пользовательского JWT имеет роль
   `anon` и доступа к этим занятиям не получает.
3. **Database → Extensions**: проверьте `pgcrypto`. Миграция сама создаст его в
   `extensions`, если расширение отсутствует. Если оно уже установлено в другом
   schema, миграция намеренно остановится: не переносите расширение вслепую,
   сначала проверьте его зависимости. Типичный Supabase использует `extensions`.
4. **SQL Editor → New query**, роль **postgres**. Откройте файл
   `migrations/20261117000100_lesson_sessions.sql` из этого репозитория, скопируйте
   **весь** файл, включая `BEGIN`/`COMMIT`, и вручную нажмите **Run**.
   Не вставляйте `.env` или ключи. SQL не требует подстановки URL/ключей.
   При ошибке исправьте причину и откатите оставшуюся открытую транзакцию командой
   `ROLLBACK`, если редактор сообщает об aborted transaction. Частичная схема не
   должна оставаться: все DDL-изменения входят в одну транзакцию.
5. Запустите отдельно **read-only** файл `verify.sql`. Ожидаются RLS=true у четырёх
   таблиц (три основные и служебный лимитер), пять RLS-политик; флаги с именем
   `must_be_false` — false, `must_be_true` — true. Все definer-функции имеют
   `search_path=""` и доверенного владельца postgres.
6. **Database → Publications** (в некоторых версиях Dashboard — настройки
   Realtime/Replication): проверьте `supabase_realtime → public.lesson_notes`.
   Миграция добавляет таблицу сама; остальные таблицы в publication не удаляет.
7. **Project Settings → Data API / API → Exposed schemas**: служебный schema
   `englishnotes_private` **не добавляйте**. Достаточно существующего `public`.
8. Перед публичным доступом проверьте Auth rate limits и включите CAPTCHA для
   anonymous sign-ins. Планируйте внешний/IP rate limiter для публичного join
   endpoint: SQL-лимит по UUID не ограничивает множество новых анонимных аккаунтов.

Это одноразовая первая миграция, не идемпотентный seed. Не запускайте её повторно
поверх созданной схемы и не удаляйте таблицы ради повторного применения.
Если используете Supabase CLI позже, Dashboard-запуск не записывает файл в историю
CLI автоматически: согласуйте migration history перед `db push`; повторного DDL
этого файла выполнять не нужно. CLI сейчас не вызывается.

**Не запускайте `tests/bootstrap.sql` или `tests/security.sql` в боевом Dashboard.**
Они предназначены только для изолированной тестовой базы. SQL Editor работает с
административными правами; успешный SELECT под postgres сам по себе не доказывает RLS.

## Модель и связь с существующим SQLite

| Объект | Облачные поля и правила |
|---|---|
| `lesson_sessions` | UUID, title, created_by (auth.users), invitation_code_hash, created_at, invitation_expires_at, status active/closed |
| `lesson_members` | lesson_id, user_id, role teacher/student, joined_at; состав меняется только серверными RPC |
| `lesson_notes` | UUID, lesson_id, author_id, title, content, position, created_at, updated_at, revision, deleted_at |

Изучена текущая SQLite schema v1: `lessons` и `notes` содержат UUID, title,
created_at/updated_at, revision и deleted_at; заметка также содержит lesson_id/content.
Поэтому облачные заметки дополнительно сохраняют title, revision и tombstone.
Позиция — неотрицательное bigint; она не обязана быть уникальной. Будущий клиент
должен сортировать по `(position,id)` и определить стратегию перестановок.

SQLite не меняется. Локальные занятия не импортируются автоматически. RPC создаёт
серверный UUID занятия; будущий адаптер должен явно связать его с локальным UUID
или реализовать отдельный безопасный импорт. Автор и учётная запись у текущих
локальных заметок отсутствуют — это также решается при проектировании синхронизации.
Облачная revision автоматически увеличивается при UPDATE; это ещё не CRDT и не
автоматическое разрешение конфликтов. Будущему клиенту нужна условная запись по
ожидаемой ревизии и обработка конфликта.

## RPC-контракт

Обе функции вызываются после `signInAnonymously()` (или другого Supabase-входа)
через пользовательский JWT. Нужны только SUPABASE_URL, publishable key и JWT
текущего пользователя. Service-role, secret key и пароль БД в клиенте не нужны.

### create_lesson_session

Аргументы RPC:

```json
{"p_title":"English lesson","p_creator_role":"student","p_invitation_ttl":"30 minutes"}
```

`p_creator_role` и TTL необязательны; defaults student и 30 минут.
TTL от 1 минуты до 24 часов. Роли — обозначения участников, не доказательство
профессии и не административные привилегии. Создатель может выбрать teacher;
подключившийся получает противоположную роль. Оба могут редактировать заметки.

Возвращается массив из одной строки:

```text
[{lesson_id: UUID, invitation_code: 64 hex chars,
  invitation_expires_at: timestamptz, outcome: "ok"}]
```

Код создаётся `pgcrypto.gen_random_bytes(32)` (256 бит), возвращается создателю
один раз. В таблице хранится только SHA-256; хеш недоступен обычному клиентскому
SELECT. Коротких/последовательных PIN-кодов нет. Передавайте код только нужному
участнику по защищённому каналу, не пишите его в публичные логи/URL.
Нельзя предотвратить доступ человека, которому добровольно передали действующий
код: до первого join он является bearer-приглашением.

Создание занятия и членства создателя атомарно. После пяти созданий в минуту
RPC возвращает `outcome="rate_limited"` и null в остальных полях.
Ошибки авторизации — SQLSTATE 42501, неверные параметры — 22023.

### join_lesson_session

```json
{"p_invitation_code":"код, полученный от создателя"}
```

Код нормализуется (внешние пробелы, регистр hex), проверяется авторизация,
действительность приглашения, активность занятия и свободное место. Занятие
блокируется `FOR UPDATE`; второе место выдаётся только одному запросу.
UNIQUE по `(lesson_id,role)` и два допустимых значения role дополнительно
ограничивают занятие двумя участниками. Срок проверяется после взятия блокировки.
При успешном join хеш и срок удаляются: приглашение становится недействительным.
Для повторного входа участник использует свою сохранённую Auth-сессию, а не код.

Ответ: `[{lesson_id: UUID, outcome: "ok"}]` либо
`[{lesson_id: null, outcome: "invalid_invitation" | "rate_limited"}]`.
Неверный, просроченный, использованный код, заполненное или закрытое занятие
дают одинаковый `invalid_invitation`, без раскрытия ID/названия/состава.
Повторный join по использованному коду также возвращает этот отказ.

У каждого UUID первые пять join-вызовов за фиксированное минутное окно разрешены;
дальнейшие возвращают rate_limited. Окно отсчитывается от первого вызова.
Учитываются и удачные, и неудачные вызовы. Возврат отказа намеренно не является
исключением — иначе попытка откатилась бы вместе с транзакцией.
**HTTP 200 не означает подключение: проверяйте поле outcome.**
Глобальную/IP-защиту, CAPTCHA и защиту от массового создания Auth-пользователей
нельзя заменить одним SQL-счётчиком. Высокая энтропия делает угадывание
действительного кода вычислительно непрактичным; обещания абсолютной защиты
от DDoS/кражи приглашения эта миграция не даёт.

## Доступ к таблицам и Realtime

- Сессия/состав/заметки доступны только участникам соответствующего занятия.
  `lesson_sessions` нужно выбирать явными колонками, **не SELECT \***:
  `id,title,created_by,created_at,invitation_expires_at,status`. Хеш исключён из grants.
- INSERT заметки требует текущего автора и членства в активном занятии.
  UPDATE разрешён обоим участникам, включая чужие заметки. Меняются только
  title/content/position/deleted_at. Нельзя менять ID, занятие, автора, created_at,
  updated_at или revision; последние два выставляются триггером.
- Физический DELETE заметок закрыт: используется tombstone `deleted_at`.
  Это даёт фильтруемые по RLS UPDATE-события и сохраняет основу будущего обмена.
- У закрытого занятия заметки читаются участниками, но не редактируются.
  Закрытие/переименование занятия, ротация приглашения, выход и замена участника
  пока не имеют клиентских RPC и относятся к следующему проектированию.
- Только lesson_notes добавлена этой миграцией в `supabase_realtime`.
  RLS SELECT остаётся обязательной при Postgres Changes с пользовательским JWT;
  REPLICA IDENTITY DEFAULT оставляет ключ для old-row, полного before-image нет.
  Обычный клиент не может делать DELETE. Административные DELETE-события могут
  иметь иные ограничения фильтрации Realtime — не используйте их для клиентского обмена.
- Подписка на Realtime, обновление JWT подписки и повторная загрузка пропущенных
  изменений пока не реализованы. Начальная загрузка/догрузка потребует того же RLS.

Definer-функции используют пустой search_path и квалифицированные имена.
EXECUTE для PUBLIC/anon отозван; пользователь может вызвать только две RPC и
два private helper-а политик (они возвращают только факт **его** членства/редактирования).
Лимитер и trigger-функция не являются клиентскими RPC. Helper-ы исключают
рекурсивную RLS на lesson_members. Владелец функций/таблиц — доверенный postgres;
роль клиентского API не должна становиться владельцем и получать BYPASSRLS.

Анонимная Auth-сессия должна сохраняться будущим приложением. При её потере новый
анонимный вход создаст другой UUID и доступа не получит. Восстановление/привязка
аккаунтов пока не реализованы. FK RESTRICT у создателя/автора защищает данные
от неявного удаления пользователя; очистку anonymous accounts с занятиями
нельзя включать без отдельной стратегии жизненного цикла.

## Проверки и сценарии отказа

Ручная команда для разработчика (Docker с Linux containers, Python 3.14):

```text
python supabase/tests/check_sql.py
```

Скрипт создаёт уникальный изолированный PostgreSQL 16 без опубликованных портов,
применяет тестовые Auth-заглушки и миграцию **только в нём**, проверяет права
под настоящими ролями anon/authenticated, делает пять гонок за последним местом
и 12 параллельных вызовов лимитера. Контейнер удаляется в finally. `.env`, Supabase
и SQLite не используются. Для нестандартного Docker socket доступен --docker-host.

Файлы `bootstrap.sql` и `security.sql` не запускаются обычными тестами приложения.
Последний использует транзакцию с ROLLBACK, но всё равно предназначен только для
тестовой БД: он создаёт тестовых пользователей и helper-функции.

После ручного применения в отдельном тестовом Supabase-проекте проверьте ещё
реальные anonymous JWT в **трёх независимых Auth-контекстах**:

| Действие | Ожидается |
|---|---|
| Один publishable key, без sign-in | Нет чтения таблиц и вызова RPC |
| A создаёт занятие | A сразу участник, получает длинный код |
| B до join читает занятия A | Пустой результат |
| B подключается действительным кодом | Участников ровно двое, роли противоположные |
| B меняет текст заметки A | Успех, автор прежний, revision увеличивается |
| C читает/меняет заметки A/B | Чтение пустое; UPDATE 0 строк, INSERT запрещён |
| C подставляет себя в lesson_members | Permission denied |
| Клиент меняет author_id/lesson_id/revision | Permission denied |
| Просроченный/неверный/использованный код | invalid_invitation без сведений о занятии |
| Два join одновременно | Один ok, второй invalid_invitation, участников два |
| Шестой join за минуту одним UUID | rate_limited, счётчик не откатывается |
| Realtime A/B и C подписаны на чужой lesson_id | A/B получают UPDATE, C не получает заметку |

Локальный PostgreSQL проверяет SQL/транзакции/RLS. Supabase Auth API, PostgREST
schema cache и доставка Realtime в облаке требуют этой отдельной проверки;
локальные Auth-заглушки не заменяют её. Сервисный ключ для тестирования RLS
использовать нельзя: он обходит политики и даёт ложноположительный результат.
